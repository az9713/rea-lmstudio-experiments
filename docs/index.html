Why you might use it

You change a response setting and get a better answer. Later you want to repeat it, but cannot remember the complete request or whether the same model settings were actually loaded. A screenshot of a settings panel leaves many of those questions unanswered.

A concrete example. The saved examples change one requested response setting, temperature, which controls sampling randomness. The comparison shows that requested difference separately from the replies. It also leaves missing model or runtime details marked unknown, rather than claiming that the setting alone caused the different answer.

1. Choose and run a request

Select an endpoint, model and supported settings in the app, then explicitly load and run the request.

2. Inspect the record

Compare what you requested with what the server confirmed. Keep the request, response and reported settings together.

3. Compare or try again

Compare saved runs, or ask to repeat a configuration after checking the newly reported settings. The same settings do not guarantee the same answer.

What this page shows. The page displays two saved simulator runs. It does not connect to your LM Studio server or generate a live AI response.

Where it runs and what is still untested. The Windows app was tested with a program pretending to be an LM Studio server. A real LM Studio model run has not been verified. No model is bundled, and the results shown here are not a speed or answer-quality benchmark.

Tests use a controlled loopback HTTP stub. Real HttpClient traffic, native UI and bundle integrity were exercised. No LM Studio model inference, installed-build parity, GPU performance or real tool execution was tested.

01 / A native experiment record

Three evidence classes.
One inspectable run.

Configure a loopback endpoint, model key, load options and inference request. Explicitly load and run, then review the load echo, stored request/response bodies, identities and lifecycle.

The API already provides useful observability. This workbench turns those existing responses into immutable local artifacts and conservative comparison/replay policies.

01 / REQUESTED

Exact sent JSON

Prompts, load settings, sampler requests and plugin declarations are committed by length and SHA-256. Credential headers are omitted.

02 / REPORTED

Server evidence

Load configuration echo, model metadata, instance IDs, outputs, tool response items and statistics are preserved with representation labels.

03 / UNKNOWN

Limits stay visible

Model-file fingerprints, engine builds, complete applied sampler settings and tool code/schema identities are not inferred.

03 / Replay is a scoped operation
Replay the configuration.
Do not imply identical outputs.
The guard requires an intact completed bundle, unchanged requested fields, matching load echoes and no plugins. A new load echo is checked again before chat; a mismatch or missing value stops that guarded replay.
The model may already be loaded when the new echo fails. Unknown file/runtime identity and backend/hardware state remain warnings even when configuration replay is allowed. A companion checksum is not a signature.
Changed factorsNew prompt, model, endpoint, settings, timeout or nested plugin fields make this a new experiment.
Incomplete evidenceFailed/canceled runs and missing/differing load echoes block replay.
Plugin side effectsAutomatic plugin replay is blocked. Explicit new runs may execute declared backend plugins.
Unknown identityFile SHA-256, engine build and tool implementation hashes stay unknown. Configuration equality is not full-state equality.


04 / Failure is evidence
Client cancellation
does not stop a backend.
A test deliberately lets the synthetic backend finish after HttpClient times out. The bundle records client_timeout or client_canceled and explicitly marks backend completion unknown.
Protocol/network failure after a load/chat attempt can also leave work running. The client neither claims backend cancellation nor automatically unloads shared models.
Headers/tokens are excluded from records. Known credentials are redacted before persistence. Non-JSON/over-depth bodies are omitted; oversized bodies fail. Exports can still contain sensitive prompts, outputs, metadata and tool results.

05 / Try the portable build
Own the client.
Choose the backend explicitly.
  1. Extract the Windows x64 release and open experiment-workbench.exe.
  2. Independently start a compatible LM Studio native v1 server. Enter its loopback URL and exact model key.
  3. Set requested controls, optional masked token and an output parent.
  4. Press Load model + run. Review the reported config, payloads and limits.
  5. Compare/export bundles, or inspect the replay guard before a new run.
No server is contacted at startup. The client permits loopback HTTP only, disables proxies/redirects/cookies, and has no model downloader. Plugin implementations may independently access networks or mutate state.

06 / Limits and source contract
Existing APIs first.
What this project contributes
LM Studio's native API already exposes loading, configuration echoes, model metadata, chat/MCP output and statistics. This independent client adds immutable artifact commitments, requested-factor accounting, terminal lifecycle records and scoped replay policies. It is not a binary patch or model/runtime extraction.
What was not validated
No real LM Studio server or installed model was probed. No inference quality, native installed-build compatibility, tool execution, GPU metrics or deterministic replay was established. File/runtime/tool identities and complete applied sampler configuration remain unknown. Source contracts do not prove implementation parity.
What checksums cannot establish
Checks detect changes against their commitments. Someone who rewrites every file can regenerate the adjacent hash. Preserve the digest independently for stronger rewrite detection. No signing, trusted timestamp or capture/backend authenticity is claimed. Linked ancestors, concurrent filesystem replacement and adversarial local processes are outside protection.
